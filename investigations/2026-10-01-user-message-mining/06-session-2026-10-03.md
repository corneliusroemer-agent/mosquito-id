# 2026-10-03: what Cornelius changed about how agents should work

**Corpus.** His own messages on 2026-10-03 only, from two agent stores: Claude Code
(`3c49558c-…jsonl`, 379 non-sidechain `type=="user"` messages after the noise filter) and the
Antigravity CLI (`~/.gemini/antigravity-cli/history.jsonl`, field `display`, 01:12–03:20 UTC —
the work Claude took over at 01:55). Timestamps below are CEST, as written in the records.

**Contamination.** 137 of the 379 Claude messages are harness noise, not Cornelius: the
"Coordinator review tick" and "Supervisor check-in" reminders that agents and Stop hooks inject as
`type=="user"`, plus `/compact`, compaction summaries and goal echoes. They are excluded
throughout. A fifth contamination class matters here and was not in the earlier reports: **the
Stop-hook feedback loops restate his goal text verbatim every few minutes**, so a phrase can appear
four times without him saying it four times. Counts are conversations, not messages.

**What this session is.** Nineteen hours, one app, six agents at peak, and roughly thirty distinct
changes to how he wants the work run. Nearly every one was **reactive** — an agent did the wrong
thing and he corrected it. That is the pattern: the preferences below are not a philosophy stated
in advance, they are a record of corrections, so each row is a rule that was broken at least once.

## 1. Ship continuously. A push is not a milestone, it is a heartbeat.

**Rule.** Commit and push continuously and in small pieces, not at the end of a task. He tests
against what is live; work that exists only in a working tree or on a branch is work he cannot
test, so it is work that has not happened.

**Quotes.**
- 02:52: *"ok have you pushed to github already let's keep it flowing so we have latest always on github link"*
- 02:53: *"hmm can you commit something that works though? keep committing please"*
- 03:34: *"now see that you commit a new thing and push, you can ask agents if they can get something pushable done tell you then we commit and push"*
- 06:05: *"why haven't we committed and pushed? i don't undersatnd"*
- 07:16: *"is nothing still pushed? keep pushing svelte subagents on the port, just supervise well, checkins every 5 min"*
- 15:51: *"i don't know why i need to push? agents should always commit in corneliusroemer-agent repos not corneliusroemer"*

**Status: extended, not new.** `02-standing-corrections.md` has no shipping-frequency rule. The
related 2026-09-08 quote in that file — *"can you push it to a branch so i can see (but don't make
a draft pr)"* — is about **visibility**, which is a weaker requirement than this.

**Cost.** Six separate times he had to ask. The temporal-progression report counted nine commits
stranded on unmerged branches at the end of the day, and one full feature (the adjacent-taxa
work: *"this is not a mosquito"*) sat complete, pushed and unmerged while he believed it was live.

**Scope.** This is about *cadence*, not about merging. See §9.

## 2. Don't let verification be the enemy of progress

**Rule.** If you think you have a fix, push it. Perfect verification is not a precondition for
shipping; it is a separate, later activity. Corollary: a green check is not evidence unless the
check would fail on the buggy code.

**Quotes.**
- 05:10: *"push if you think you might have a fix, don't let verification be the enemy of progres"*
- 05:18: *"get one subagent to just do that and done. no need to test extensively just do it commit it push it"*

**Why it exists.** The 05:10 correction came immediately after a long stretch of the agent holding
back. Nine minutes earlier he had overridden an agent that refused to download a model on
prioritisation grounds — a refusal that cost more time than the download would have.

**The paired rule, which is not optional.** Two tests this session were green and measuring
nothing. One asserted only that two imported symbols were the same object; another aborted
`text_embeds*.json` alongside the model, so the render path never executed. The fix adopted was to
run each new test **against the unfixed code and confirm it fails there** — which later turned
into the "verified by served bytes, not by the repo" discipline. **Push unverified; never claim
unverified.** Shipping and saying so are separate decisions, and he wants the first loose and the
second strict.

## 3. Prioritisation is a recommendation, not a veto

**Rule.** An agent that decides not to do something, because it judged the work low-value, has
overstepped. Its job is to make the case and proceed.

**Quotes.**
- 05:43: *"why would the agent block a download that's stupid"*
- 05:43: *"nonono it should just try it: And it refused to download SigLIP, reasoning that if the MA probe shows data was the binding constraint, a third contrastive variant stops mattering. That's better prioritisation than I gave it."*

**Note the shape of the correction.** He quotes the agent's reasoning back verbatim and agrees with
its logic, then overrides it anyway. He is not saying the reasoning was bad; he is saying the
conclusion was not the agent's to reach.

**The same rule, pointed the other way.** 05:15: *"our app is honestly so small that we shouldn't
make a big thing out of it… the question is more _which_ framework and tooling to use not whether
to"*. And 05:23: *"come on those costs are a joke we've written this page in 2hr let's not
exaggerate that's ridiculous"*. An agent that over-scopes has the same defect as one that
under-scopes: both substitute its own judgement for his.

## 6. Supervision is a reporting protocol, not a vibe

**Rule.** Three things, all stated as requirements.

**(a) Ask for updates on a clock.** 04:53: *"ask your subagents always for updates every 10min or so
so you know what they're up to, if they've hit issues"*. Tightened to five minutes at 07:16.

**(b) "Fine" is not a status report.** 05:23: *"yeah agents need to say more than fine, they need to
explain what they're doing, how it fits into the goal they were given, why they think it's worth to
keep going what they expect to learn in the next work they're doing"*.

**(c) You decide whether it continues.** 05:22: *"get them to give you updates regularly and you
decide whether it's worth going or not"*. The coordinator is a decision-maker, not a relay.

**Status: extended.** `03-meta-tooling.md` already covers dispatch and wrap-up. What is new is
(b): agents in this session repeatedly reported "in progress, all fine" and were corrected for it,
which makes the *content* of a status report load-bearing.

## 7. Agents get ~45 minutes, then hand off

it drift.

**Status: extended.** `03-meta-tooling.md` records wrap-up-and-hand-off from 2026-08-29→09-30. The

## 8. Subagents may spawn their own subagents — for independence, not throughput

**Quote.**
- 13:40: *"I think you can give each agent the chance to call up to 2 subagents that are targeted - most useful they are when they should give independent perspective like adversarial review or helping one get unstuck or reconsider priorities. while subagents should report to you regularly, for certain things it's better that they instead get a dedicated agent with less context to narrowly check something or evaluate something from a perspective that might be colored/biased by how we've been doing things"*

**The reasoning is the rule.** An agent with your context inherits your framing. A fresh agent
asked to check one narrow thing does not. That is also why 13:42 asked for a subagent to trace the
project's temporal progression *"just good to have this to get others independent outsiders to
weight in"*, and why he passed his own reviewer's critique of a report back to the coordinator at
12:18 rather than acting on it himself.

## 10. Long computation is fine; waiting on it is not

**Quotes.**
- 15:20: *"we seem to use very little cpu right now? maybe you're too strict on the compute instructions"*
- 15:42: *"i see some tunings/distillations might need 2hr of cpu time - that's not necessarily prohibitive we can run over night for example and have a single one use 80% cpu for example that's ok - i could also run it outside of docker on mlx gpu for example to speed up if it's well contained and runnable. so don't let agents assume they have only 45 min, if they can make a case we can do more computational stuff for sure"*

**Scope, and the contradiction it resolves.** This collides head-on with §7, in the same message,
thirty seconds apart: *"don't let agents assume they have only 45 min"* alongside *"prefer fresh ones
after 45min"*. Two different objects.

- **§7 is about agent lifetime.** A subagent is a context window with a cost. At 45 minutes it has
  usually lost more than it has gained, so wrap it and start fresh. The unit is a person's-context.
- **§10 is about job runtime.** A distillation run is a batch job with no context to lose. Two hours
  of it costs him nothing and is worth starting tonight.

**The rule that reconciles them:** *never refuse to start a computation because it is long, and
never let an agent keep running because it is nearly done.* Long jobs run detached; agents hand off
on a clock. His own framing of §10 is the tiebreak: **make the case and ask** — *"if they can make a
case we can do more computational stuff for sure"* — so the default is permissive and the burden is
on the agent to show the work is worth the time.

**A third rule, same family, 15:21:** *"it's very cool that the small model can be tuned so well - we
should put that into prod/previews immediately so one can testdrive it"*. An improvement that exists
only in a report has not been made. Make it testable.

## Where the record is too thin

- **"Draft PRs are for Loculus work only" has no message behind it.** I searched the full
  2026-10-03 corpus, the last sixty transcripts, and the memory notes. Every draft PR in this
  session was an agent's choice or an inherited rule; the coordinator said at 16:21 *"it's a
  non-draft PR by design so I merge rather than racing the other agents"*, which describes a
  practice, not a permission he granted. **Do not record this as his rule on the strength of the
  instruction to open one.** It is consistent with `AGENTS.md`'s draft-everything rule being relaxed
  for this repo, and that relaxation is worth confirming with him.
- **One correction is thinner than it looks.** 05:23 *"those costs are a joke"* and 05:35 *"don't
  use those costing hours"* are two messages about the same complaint, not two incidents. The
  second is about method choice, not about time.
- **No message today about "a green test that measured nothing being worse than no test."** The two
  vacuous tests were found and reported by an agent at 09:32, and the coordinator relayed it at
  15:08. He did not state it as a rule and did not correct anyone for it. The rule is real and
  well-supported (§2) but it is the coordinator's inference, not his words.
- **The 45-minute figure is a preference, not a measurement.** It appears once, at 16:13, with no
  account of what the long-lived agents had actually done wrong beyond drift. Treat it as a
  default to check against context, not a law.
